# 스크린샷 인식 방법 (팀 미리보기 → 상대 6마리)

매치업 탭의 "스크린샷으로 입력"이 팀 미리보기 스크린샷에서 상대 포켓몬을 읽는 방법이다.
이 문서만 읽어도 다른 세션(AI 포함)이 방법을 이해하고, 고치거나 다른 곳에 응용할 수 있게 정리했다.
화면에서 쓰는 방법과 사용자 요청 사항은 [features.md](features.md)의 "스크린샷으로 상대 입력"에 있다. 처음 만든 커밋은 106643b다.

## 한눈에 보기

- **서버도 외부 API(AI 이미지 인식 포함)도 쓰지 않는다.** 브라우저가 canvas로 스크린샷의 픽셀 값(RGBA 숫자 배열)을 꺼내 JavaScript로 직접 계산한다. 스크린샷은 기기 밖으로 나가지 않는다.
- **그림을 저장해 두고 맞춰 보는 방식도 아니다.** 저장소에 넣은 것은 포켓몬마다 숫자 55개다: 성별 비율 1개와, HOME 3D 그림(일반·이로치)의 "색 요약" 27개씩.
- 방법의 뼈대는 네 가지다.
  1. 확실하게 읽히는 단서(타입 아이콘 색, 성별 표시)로 후보를 **거른다.**
  2. 불확실한 단서(그림의 색 분포)로는 후보의 **순서만** 정한다.
  3. 결과를 바로 쓰지 않고 **사람이 확인하고 고친다.**
  4. 고른 결과를 그림 **지문으로 기억**해서, 다음에 같은 그림이 나오면 바로 맞춘다.
- 타입과 성별을 맞게 읽으면 정답은 항상 후보 안에 있다. 색 비교가 틀려도 정답의 순서가 밀릴 뿐이다.

## 1. 풀어야 했던 문제

- 챔피언스의 팀 미리보기에는 **포켓몬 이름이 나오지 않는다.** 상대 칸(진한 빨간 칸)마다 다음만 있다.
  - 왼쪽: 포켓몬 그림 (게임 속 3D 모델)
  - 오른쪽 위: 타입 아이콘 1~2개. 왼쪽이 첫 번째 타입이다.
  - 오른쪽 아래: 성별 표시 (♂ 파랑, ♀ 빨강). 성별이 없는 포켓몬은 표시가 없다.
- 게임 속 그림은 공식 일러스트나 HOME 3D 그림과 **자세가 다르다.** 모양을 맞춰 보는 비교(템플릿 매칭)는 쓸 수 없다.
- **이로치**(색이 다른 개체)가 있어서 색만 믿을 수도 없다.
- 사이트는 GitHub Pages의 정적 사이트라 서버가 없다. 공개 저장소라서 프론트 코드에 API 키를 넣을 수도 없다.
- 게임 속 그림을 모아 둔 공개 데이터가 없다. 있더라도 저작권 때문에 저장소에 넣지 않는다.

## 2. 전체 흐름

```
[npm run data, Node]  데이터를 만들 때 한 번
  PokeAPI/sprites 저장소의 HOME 3D 그림 (기본 모습 265개 × 일반·이로치)
    → scripts/png.mjs 로 디코드 → colorFeature (src/spriteFeature.ts)
    → src/data/recognition.json  { key: { gender, normal[27], shiny[27] } }

[브라우저]  "스크린샷으로 입력"을 누를 때
  파일 → createImageBitmap → canvas → getImageData (RGBA 배열)
    → analyzeTeamPreview(이미지, 기억)          src/teamPreview.ts
        ① 칸 찾기                               findPanels
        칸마다
        ② 그림 위치, 색 특징, 지문              readSprite
        ③ 타입 아이콘                           readTypes
        ④ 성별 표시                             readGender
        ⑤ 후보 거르기: 타입 + 성별              recognition.json 의 gender
        ⑥ 후보 순서: 색 특징 비교               recognition.json 의 normal / shiny
        ⑦ 기억 확인: 지문 비교                  localStorage 의 sprite-memory
    → 확인 화면: 칸마다 잘라 낸 그림, 읽은 타입·성별, 후보   src/components/ScreenshotImport.tsx
    → "이 N마리로 바꾸기": 상대 목록 교체 + 고른 결과 기억    src/spriteMemory.ts
```

- 분석 코드와 `recognition.json`은 동적 import로 나뉜 파일(약 46KB, gzip 약 12KB)이다. 이 기능을 처음 쓸 때만 내려받는다.
- 스크린샷 한 장을 분석하는 데 PC에서 약 0.1초 걸린다.
- 위치와 크기는 모두 칸의 너비·높이에 대한 비율로 정한다. 그래서 해상도나 자른 범위가 달라도 같은 코드로 읽힌다.

## 3. 단계별 방법

### ① 칸 찾기 (`findPanels`)

- 칸 바탕색 판정 `isPanel`: `r ≥ 60`, `g ≤ 45`, `20 ≤ b ≤ 110`, `r > 1.1 × b` (진한 빨강~자주)
- 열마다 칸 바탕색 비율을 센다. 가장 큰 값이 5% 미만이면 칸이 없다고 보고 끝낸다. 화면에는 "상대 칸을 찾지 못했어요"가 나온다.
- 비율이 가장 큰 값의 절반 이상인 첫 열부터 마지막 열까지를 칸의 열 범위로 잡는다.
- 그 범위 안에서 줄마다 칸 바탕색 비율이 25%를 넘는 줄이 이어진 구간을 칸으로 본다. 3줄까지 끊겨도 이어진 것으로 본다.
- 높이가 열 범위 너비의 20% 미만인 구간은 버린다 (위쪽 이름표 같은 얇은 띠).
- 높이가 중앙값 ±30% 안인 구간만 남기고, 위에서부터 6개까지 쓴다.
- 칸마다 좌우 끝을 넓힌다. 그 열의 칸 바탕색 비율이 30%를 넘는 동안 계속 넓힌다.
- 전제: 상대 칸이 세로로 한 줄로 쌓여 있다.

### ② 그림 (`readSprite`)

- 칸의 왼쪽 4~62%, 위아래 4% 안쪽을 본다. 칸 바탕색도 붉은색(`isCrimson`, ⑥ 참고)도 아닌 픽셀을 그림으로 본다.
- 가로·세로 좌표를 각각 1%와 99% 지점에서 잘라, 튀는 점을 빼고 그림 사각형을 잡는다. 확인 화면의 작은 그림은 이 사각형을 96px로 잘라 만든다.
- 여기서 두 가지를 만든다.
  - **색 특징**: ⑥에서 후보 순서를 정할 때 쓴다.
  - **지문**: ⑦에서 기억과 비교할 때 쓴다.

### ③ 타입 아이콘 (`readTypes`)

- 칸 너비의 55% 지점부터 오른쪽 끝까지, 높이 3~50% 영역을 본다.
- 아이콘 픽셀은 칸 바탕색이 아니고, 가장 밝은 채널이 60 이상인 픽셀이다 (어두운 그림자는 뺀다).
- 열마다 아이콘 픽셀이 영역 높이의 30%를 넘으면 아이콘 열이다. 이어진 아이콘 열을 한 묶음으로 본다.
- 아이콘은 거의 정사각형이라, 묶음 너비가 칸 너비의 8~25%인 것만 아이콘으로 인정한다.
- 아이콘이 오른쪽에 붙어 있어서 마지막 두 묶음까지만 쓴다. 왼쪽 묶음이 첫 번째 타입이다.
- 아이콘 색은 묶음 안 아이콘 픽셀의 채널별 중앙값이다. 흰 무늬(세 채널 모두 216 이상)는 뺀다.
- `src/pokemon.ts`의 `TYPES` 색(앱의 타입 칩 색) 가운데 RGB 거리가 가장 가까운 타입을 고른다.
  - 실제 스크린샷으로 맞는지 확인한 타입은 8가지(비행, 드래곤, 바위, 물, 전기, 고스트, 노말, 땅)뿐이다.

### ④ 성별 표시 (`readGender`)

- 칸 너비의 55% 지점부터 오른쪽 끝까지, 높이 45% 지점부터 아래 끝까지를 본다.
- 색 조건
  - ♂ 파랑: `b > 150`, `b > r + 60`, `b > g + 20`
  - ♀ 빨강: `r > 170`, `g < 90`, `b < 110`, `r > b + 80`
- 조건에 맞는 픽셀을 8방향으로 이어서 덩어리를 만들고, **동그랗게 꽉 찬 덩어리만** 인정한다. 세 조건을 모두 만족해야 한다.
  - 가로:세로가 0.6~1.6
  - 높이가 칸 높이의 8~40%
  - 둘러싼 사각형의 40%보다 많이 채움
- 인정된 덩어리 중 가장 큰 것의 색으로 성별을 정한다. 없으면 "성별 없음"이다.
- 처음에는 모양을 보지 않아서, 배경의 빨간 레이저 줄을 ♀로 읽었다(로토무 칸). 긴 선은 동그랗지 않아서 이제 빠진다.

### ⑤ 후보 거르기

- 후보는 기본 모습 265개(`BASE_POKEMON`, 메가 제외)다. 상대 메가는 매치업 표의 "상대 메가 포함"이 따로 붙인다.
- 타입은 순서까지 같아야 한다 (`types.join()` 비교).
- 성별은 `recognition.json`의 `gender`로 판단한다 (`genderMatches`). 이 값은 PokéAPI `pokemon_species.gender_rate`다. -1은 성별 없음, 0은 수컷만, 8은 암컷만이고, 1~7은 둘 다 있다.

| 읽은 성별 | 후보로 남는 포켓몬 |
|---|---|
| 성별 없음 | `gender`가 -1 |
| ♂ | `gender`가 -1도 8도 아님. key가 `-female`로 끝나는 모습은 뺀다 |
| ♀ | `gender`가 -1도 0도 아님. key가 `-male`로 끝나고 `-female` 모습도 참전하면 뺀다 |

- 냐오닉스, 에써르, 대쓰여너는 암수 모습이 따로 참전한다. 그래서 성별 표시대로 나눈다. 화염레오는 `pyroar-male`만 참전하므로 ♀도 이 모습으로 본다.
- 남는 포켓몬이 없으면(타입이나 성별을 잘못 읽었을 때) 다음 순서로 넓힌다: 타입만 맞는 포켓몬 → 타입이 하나라도 겹치는 포켓몬 → 전체
- 얼마나 줄어드나 (2026-10-30 데이터 기준)
  - 기본 모습 265개는 타입 조합 134가지로 나뉜다. 타입만으로 하나로 정해지는 포켓몬은 89개(34%)다.
  - 가장 큰 묶음은 노말 단일 12개, 물 단일 11개, 전기 단일 9개다.
  - 성별까지 보면 후보가 1개인 경우가 37%, 4개 이하인 경우가 65%다. 평균 3.7개, 가장 많을 때 11개다. 포켓몬마다 나올 수 있는 성별 표시를 하나의 경우로 셌다.

### ⑥ 후보 순서: 색 특징 (`spriteFeature.ts`)

- 그림 픽셀을 HSV(색상·채도·명도)로 바꿔 27칸 히스토그램을 만든다.
  - 채도와 명도가 둘 다 0.25 이상인 색은 색상 30°씩 12칸 × 채도 2칸(0.6 기준) = 24칸에 넣는다.
  - 나머지(흰색·회색·검정에 가까운 색)는 명도 3칸(0.35, 0.7 기준)에 넣는다.
  - 칸 값의 합이 255가 되게 맞춘다. 그래서 그림 크기와 상관없이 비교할 수 있고, 0~255 정수로 저장할 수 있다.
- **붉은색은 세지 않는다** (`isCrimson`). 색상 320° 이상이거나 12° 미만이면서 채도 0.45 초과, 명도 0.3 초과인 색이다.
  - 칸 바탕, 테두리, 배경 레이저 줄의 붉은색이 그림 영역에 섞여 들어와서 순위가 흔들렸기 때문이다.
  - 공정하게 비교하려고 HOME 그림에서도 똑같이 뺀다.
- 두 특징이 비슷한 정도는 칸마다 작은 쪽 값을 더해 255로 나눈 값(히스토그램 교집합, 0~1)이다.
- 포켓몬의 점수는 다음 둘 중 큰 값이다. 상대가 이로치인 경우는 드물어서 이로치 쪽 점수는 10% 깎는다.
  - 일반 그림과 비슷한 정도
  - 이로치 그림과 비슷한 정도 × 0.9
- 모양은 보지 않고 "어떤 색이 얼마나 있는지"만 본다. 자세가 달라도 색 분포는 비슷하기 때문이다.
- 점수 순으로 12개까지 후보로 넘긴다.
  - 확인 화면은 처음에 4개를 보여 주고, 나머지는 "후보 N개 더"를 누르면 나온다.
  - 후보에 없으면 "직접 찾기"로 기본 모습 전체에서 검색한다.

### ⑦ 기억: 그림 지문 (`spriteMemory.ts`)

- 지문은 그림 사각형을 12×12 칸으로 나눠, 칸마다 4바이트씩 담은 576바이트다. 이름은 "지문"이지만 그림을 아주 작게 줄인 것에 가깝다.
  - 앞의 3바이트: 그 칸에 있는 그림 픽셀의 평균 RGB
  - 마지막 1바이트: 그 칸에서 그림이 차지하는 비율 × 255
- "이 N마리로 바꾸기"를 누르면 칸마다 `{ key: 고른 포켓몬, print: 지문 }`을 저장한다.
  - 저장 위치는 localStorage `champions-speed/sprite-memory`(version 1)다.
  - 지문은 base64 문자열로 바꿔 저장한다.
- 지문 차이는 576바이트 값 차이(0~255)의 평균이다. 다음 분석 때 기억 중 차이가 가장 작은 것이 **20 미만**이면 같은 그림으로 본다.
  - 그 포켓몬을 후보 맨 앞에 두고 "기억한 그림"으로 표시한다.
  - 타입을 잘못 읽었어도 기억을 믿는다.
- 기준 20의 근거: 시험 스크린샷에서 같은 그림끼리는 크기·압축·자른 모양이 달라도 차이가 0~6.8이었다. 서로 다른 그림끼리는 46.8 이상(평균 69.9)이었다.
- 게임 그림끼리 비교하므로 정확하다. 이로치도 한 번 고르면 다음부터 맞는다.
- 저장할 때 차이가 20 미만인 옛 항목은 지운다. 그래서 같은 그림은 마지막에 고른 포켓몬으로 바뀐다. 300개가 넘으면 오래된 것부터 버린다.
- 읽을 때는 다음 항목을 버린다: 지금 참전 목록의 기본 모습이 아닌 것, 길이가 576이 아닌 것.
- 브라우저마다 따로 저장된다. 휴대폰과 PC는 기억을 따로 쌓는다.

## 4. 인식용 데이터 (`recognition.json`)

```json
"kangaskhan": { "gender": 8, "normal": [152, 1, 74, …], "shiny": [0, 0, 68, …] }
```

- `npm run data`(`scripts/build-data.mjs`)의 마지막 부분이 만든다. 운영 방법은 [data.md](data.md)의 "스크린샷 인식용 데이터"에도 있다.
- HOME 그림은 포켓몬 HOME 앱의 3D 그림을 PokéAPI 커뮤니티가 모아 둔 것이다.
  - 받는 곳: GitHub `PokeAPI/sprites` 저장소의 `sprites/pokemon/other/home/<pokemon.id>.png`. 이로치는 `home/shiny/` 아래에 있다.
  - 포켓몬 HOME 서버와는 통신하지 않는다. 2026-10-30에 찾아본 범위에서는 포켓몬 HOME에 개발자용 공개 API가 없었다.
- 투명하지 않은 픽셀(알파 128 이상)만 센다. 스크린샷과 같은 `colorFeature`를 쓰므로 붉은색을 빼는 규칙도 같다.
- 같은 계산 코드를 브라우저와 Node가 함께 쓴다.
  - `build-data.mjs`는 `src/spriteFeature.ts`를 Node 22에서 바로 import 한다.
  - 그래서 `spriteFeature.ts`는 다른 파일을 import 하지 않게 둔다.
- PNG는 외부 라이브러리 없이 `scripts/png.mjs`로 읽는다. Node의 `zlib`만 쓰고, 8비트·인터레이스 없는 PNG만 지원한다.
- 받은 그림 530장(약 67MB)은 `.cache/home/`에 두고 다시 쓴다. 이 폴더는 git에 올리지 않는다. 한꺼번에 받으면 실패해서 6개씩 나눠 받는다.
- 결과 파일은 44KB(gzip 9KB)다.
- **다시 만드는 때는 참전 목록이 바뀔 때뿐이다.** 주기적으로 갱신할 필요는 없다.
  - 이미 있는 포켓몬의 값은 HOME 그림이 바뀌지 않는 한 그대로다.
  - 새 포켓몬의 HOME 그림이 아직 없으면 `HOME 그림 다운로드 실패` 오류를 내고 멈춘다.

## 6. 쓰지 않은 방법과 겪은 문제

- **모양 비교**: 게임 그림을 공식 일러스트·HOME 그림과 나란히 놓고 보니 자세와 각도가 달랐다. 그래서 쓰지 않았다.
- **AI 이미지 인식 API**: 쓰지 않았다.
  - 서버가 없고, 공개 저장소라 API 키를 프론트 코드에 넣을 수 없다.
  - 스크린샷을 밖으로 보내지 않는 편이 낫다.
- **성별 오인**: 배경의 빨간 레이저 줄을 ♀로 읽었다. 동그란 덩어리만 인정해서 고쳤다.
- **색 순위 흔들림**: 칸 테두리와 레이저 줄의 붉은색이 그림 색에 섞였다. 스크린샷과 HOME 그림 양쪽에서 붉은색을 빼서 고쳤다.

## 7. 한계

- 타입 아이콘 색은 8가지만 확인했다. 나머지 10가지는 앱의 타입 칩 색으로 고르므로 잘못 읽을 수 있다.
  - 타입을 잘못 읽으면 정답이 후보에서 빠진다. 그때는 "직접 찾기"로 골라야 한다.
- 붉은색을 빼고 비교하므로 몸이 붉은 포켓몬은 후보 순서가 덜 정확하다.
- 같은 종의 다른 모습은 타입과 색이 비슷해서 순서가 불안정하다 (루가루암 세 모습 등). 한 번 고르면 기억으로 맞는다.
- 상대 칸(진한 빨간 칸)만 읽는다.
- 기억은 그 브라우저에만 남는다. 내보내기/가져오기는 없다.
- 분석 파일을 한 번도 받지 않은 상태에서 인터넷이 끊기면 파일을 불러오지 못한다. 그런데 화면에는 "상대 칸을 찾지 못했어요"라는 맞지 않는 안내가 나온다.
- 게임 업데이트로 팀 미리보기의 배치나 색이 바뀌면 ①~④의 비율과 색 범위를 다시 맞춰야 한다.

## 8. 확인하는 방법

브라우저에서 확인한다.

1. `npm run dev`로 띄우고 매치업 탭에서 "스크린샷으로 입력"으로 팀 미리보기 스크린샷을 올린다.
2. 칸마다 읽은 타입·성별과 후보를 보고, 틀린 칸을 고친 뒤 적용한다.
3. 같은 스크린샷을 다시 올려 "기억한 그림"이 붙는지 본다.

- 시험하면서 쌓인 기억은 개발자 도구에서 `localStorage.removeItem('champions-speed/sprite-memory')`로 지운다.
- 적용하면 매치업의 상대 목록(`champions-speed/opponents`)도 바뀐다. 사용자의 값이면 시험 전에 적어 두고 되돌린다.

화면 없이 숫자로 확인하려면 Node에서 Vite로 `.ts` 모듈을 불러 쓴다. 저장소 루트에서 Node 22(`nvm use`)로 실행한다.
`scripts/png.mjs`는 PNG만 읽는다. WebP나 JPEG는 먼저 PNG로 바꾼다. macOS에서는 `sips -s format png 원본.webp --out shot.png`로 바꿀 수 있다.

```bash
node --input-type=module -e "
import { readFileSync } from 'node:fs'
import { createServer } from 'vite'
import { decodePng } from './scripts/png.mjs'
const server = await createServer({ logLevel: 'error', server: { middlewareMode: true, hmr: false } })
const { analyzeTeamPreview } = await server.ssrLoadModule('/src/teamPreview.ts')
const { TYPES } = await server.ssrLoadModule('/src/pokemon.ts')
for (const s of analyzeTeamPreview(decodePng(readFileSync(process.argv[1])), []))
  console.log(s.types.map((t) => TYPES[t].name).join('/'), s.gender, s.candidates.slice(0, 5).map((p) => p.name).join(', '))
await server.close()
" shot.png
```

- `analyzeTeamPreview`의 두 번째 인자가 기억 목록이다. 기억까지 시험하려면 `{ key, print }[]`를 넣는다. `print`는 앞선 분석 결과의 `print`를 쓰면 된다.

## 9. 개선 아이디어 (제안만 하고 아직 하지 않은 것)

사용자가 고르기 전에는 시작하지 않는다.

- **실제 아이콘 색 표 만들기**: 다른 타입이 나온 스크린샷을 모아 표를 만들고, `TYPES` 칩 색 대신 이 표와 비교한다. 그러면 나머지 10가지 타입도 믿을 수 있다.
- **오프라인 안내**: 분석 파일 불러오기 실패와 칸 찾기 실패를 나눠서 안내한다. 또는 서비스 워커(PWA)로 미리 받아 둔다.
- **기억 옮기기**: 그림 기억 내보내기/가져오기 (휴대폰 ↔ PC)
- **붙여넣기로 올리기**: PC에서 Ctrl+V로 스크린샷 올리기
- **사용률로 순서 보정**: 루가루암 세 모습처럼 색이 비슷할 때, 많이 쓰이는 포켓몬을 앞에 둔다.
  - 공개된 사용률은 비공식 사이트(Champdex, MunchStats 등)뿐이다. 이용 조건을 먼저 확인해야 한다.
  - 데이터는 `npm run data` 때 받아 저장한다. 사이트가 실행 중에 밖으로 요청하지 않는 원칙을 지키기 위해서다.
- **HOME 그림 대체**: 새 포켓몬의 HOME 그림이 아직 없을 때 공식 일러스트로 대신 계산한다.

## 10. 다른 곳에 응용할 때

이 기능에서 다른 곳에도 쓸 만한 생각을 모았다.

- 이름처럼 결정적인 정보가 없으면, 확실하게 읽히는 작은 표시로 후보부터 줄인다.
- 불확실한 비교는 결정이 아니라 순서에만 쓰고, 마지막 결정은 사람에게 맡긴다.
- 사람이 고른 결과는 지문으로 저장해 두고, 같은 출처의 그림끼리 비교한다. 두 번째부터는 거의 틀리지 않는다.
- 참조 데이터는 이미지 대신 작은 숫자 요약으로 번들에 넣는다. 요약은 빌드 때 계산한다. 요약 함수는 빌드(Node)와 브라우저가 같은 코드를 쓴다.
- 위치는 픽셀 값이 아니라 찾은 영역에 대한 비율로 정한다. 그러면 해상도와 자르기에 강해진다.
- 배경 잡음(여기서는 붉은 줄)은 입력과 참조 데이터 양쪽에서 똑같이 뺀다.
